# 재고 차감 락 3종 비교

주문 생성에서 재고를 차감하는 방식 세 가지를 같은 경쟁 조건에서 돌려 보고, 운영 코드에 조건부 UPDATE를 채택한 이유를 기록한다. 이 문서의 숫자는 모두 `StockLockComparisonTest`를 3번 실행해 직접 얻은 값이다. 비교용 구현 세 개는 테스트 소스(`com.sprint.mission.product.stock`)에만 있고, 운영 코드는 조건부 UPDATE(`SkuRepository.adjustStock`)만 쓴다.

## 1. 실험 환경

| 항목 | 값 |
| --- | --- |
| 실행 환경 | 로컬 macOS(Apple Silicon), OrbStack 위의 Testcontainers |
| DB | PostgreSQL 17 (`postgres:17-alpine`), 설정은 기본값이다 |
| 커넥션 풀 | HikariCP 기본값(최대 10개) |
| 스레드 | 200개, `CountDownLatch` 하나로 동시에 시작한다 |
| 데이터 | SKU 1개, 재고 100, 스레드마다 1개씩 차감한다 |
| 검증 | 성공 100, 실패 100, 최종 재고 0, 차감 중 예외 0 (소요 시간은 검증하지 않는다) |

이 숫자는 개발 노트북의 로컬 Testcontainers에서 잰 값이며 운영 환경의 성능이 아니다. 같은 행 하나에 200개 스레드가 몰리는 최악의 경쟁을 만든 것이라 방식 사이의 상대적인 성격을 보는 용도로만 쓴다.

## 2. 구현 방식

| 방식 | 차감 방법 | 트랜잭션 |
| --- | --- | --- |
| 비관적 | `select stock from sku where id = ? for update`로 행을 잠그고, 재고가 부족하면 false, 충분하면 `update sku set stock = stock - ?`를 실행한다 | 읽기부터 커밋까지 하나로 묶고 잠금을 커밋까지 쥔다 |
| 낙관적 | 잠금 없이 `stock, version`을 읽고, 부족하면 false, 아니면 `update ... set stock = ?, version = version + 1 where id = ? and version = ?`를 실행한다. 0행이면 1~5ms 무작위로 쉬고 다시 읽는다(최대 100회, 넘기면 `IllegalStateException`) | 열지 않는다. 읽기와 쓰기가 각각 자동 커밋된다 |
| 조건부 UPDATE | `update sku set stock = stock + :delta where id = ? and stock + :delta between 0 and 100000`을 한 문장으로 실행하고, 바뀐 행이 1이면 성공이다 | UPDATE 한 문장이라 짧다 |

낙관적 락의 `version` 컬럼은 테스트 마이그레이션(`V901__sku_version.sql`)에만 있다. 운영 스키마와 `Sku` 엔티티에는 없다.

## 3. 측정 결과

3번 실행한 결과다. 재시도는 낙관적 락에서 버전 충돌로 다시 시도한 횟수의 합계다.

| 실행 | 방식 | 소요(ms) | 재시도 |
| --- | --- | ---: | ---: |
| 1 | 비관적 | 149 | 0 |
| 1 | 낙관적 | 65 | 494 |
| 1 | 조건부 UPDATE | 84 | 0 |
| 2 | 비관적 | 140 | 0 |
| 2 | 낙관적 | 92 | 489 |
| 2 | 조건부 UPDATE | 127 | 0 |
| 3 | 비관적 | 152 | 0 |
| 3 | 낙관적 | 79 | 439 |
| 3 | 조건부 UPDATE | 88 | 0 |

| 방식 | 평균 소요(ms) | 평균 재시도 |
| --- | ---: | ---: |
| 비관적 | 147 | 0 |
| 낙관적 | 79 | 474 |
| 조건부 UPDATE | 100 | 0 |

세 방식 모두 매번 성공 100, 실패 100, 최종 재고 0이었고 예외는 없었다. 낙관적 락의 재시도 상한(100회)에 걸린 스레드도 없었다.

### 결과 해석

- 이 측정에서 단순 소요 시간은 낙관적, 조건부 UPDATE, 비관적 순으로 짧았다. 조건부 UPDATE가 가장 빠르지 않았다는 점을 숨기지 않는다.
- 낙관적 락이 빠르게 끝난 것은 재고가 0이 된 뒤의 실패 100건이 잠금과 트랜잭션 없이 SELECT 한 번으로 끝나고, 커넥션을 오래 쥐지 않아서다. 읽기와 쓰기 사이에 다른 작업이 없어서 충돌 비용도 작다. 대신 성공 100건을 얻는 데 충돌 재시도가 평균 474회 일어났다.
- 비관적 락은 스레드 200개가 풀 10개를 놓고 줄을 서고, 잠금을 쥔 채 SELECT와 UPDATE 두 번 왕복하므로 가장 느렸다.
- 한 번에 실행하는 시간이 100~150ms 수준이고 실행 사이 편차(조건부 UPDATE 84~127ms)도 커서, 방식 사이의 작은 차이를 순위로 읽으면 안 된다. 각 실행에서 비관적이 가장 먼저 돌았기 때문에 JVM과 커넥션 풀이 데워지는 비용이 비관적 쪽에 실렸을 가능성이 있다.

## 4. 방식별 장단점

| 항목 | 비관적 | 낙관적 | 조건부 UPDATE |
| --- | --- | --- | --- |
| 트랜잭션 길이 | 가장 길다. 읽기부터 커밋까지 행 잠금을 쥔다 | 짧다. 잠금을 쥐지 않는다 | 가장 짧다. UPDATE부터 커밋까지만 잠근다 |
| 재시도 비용 | 없다. 대신 대기한다 | 크다. 충돌할수록 재시도가 늘고, 상한을 넘으면 실패 처리가 필요하다 | 없다. 부족하면 바로 0행이다 |
| 다중 SKU 데드락 | 잠금 순서가 어긋나면 데드락이 난다. id 순서를 강제해야 한다 | 잠금이 없어 데드락은 없다. 대신 SKU마다 충돌과 재시도를 따로 다뤄야 한다 | UPDATE가 행 잠금을 쓰므로 순서가 어긋나면 데드락이 난다. id 순서를 강제해야 한다 |
| 코드량 | 중간. 잠금 쿼리와 부족 검사를 직접 쓴다 | 가장 많다. version 컬럼, 재시도 루프, 대기, 상한 처리가 필요하다 | 가장 적다. 쿼리 하나와 반환값 검사다 |
| 스키마 | 변경 없음 | 운영 마이그레이션에 version 컬럼이 필요하다 | 변경 없음 |
| 주문 트랜잭션과의 조합 | 주문 생성 내내 재고 행 잠금을 쥔다 | 재시도하려면 읽기부터 다시 해야 해서, 주문 트랜잭션 안에서 쓰기가 어렵다 | 주문 트랜잭션 안에서 문장 하나만 실행하면 된다 |

## 5. 채택 이유

운영 코드는 조건부 UPDATE를 쓴다.

- 단일 행 차감은 조건부 UPDATE 한 문장이 행 잠금을 가장 짧게 잡는다. 읽고 계산해서 쓰는 대신 DB가 한 문장으로 계산하므로 갱신이 사라지거나 재고가 음수가 되는 일이 없다.
- 주문은 쿠폰·적립금 처리 같은 다른 작업과 한 트랜잭션에 묶인다. 비관적 락은 그 트랜잭션이 끝날 때까지 재고 행을 막고, 낙관적 락은 충돌 시 읽기부터 다시 해야 한다. 조건부 UPDATE는 이 두 문제가 없다.
- 위 측정에서 낙관적 락이 더 빨랐지만, 이는 읽기와 쓰기 사이에 다른 작업이 없는 단순한 경쟁에서의 결과다. 주문 트랜잭션에 넣었을 때의 재시도 복잡도, 운영 스키마 변경, 충돌이 늘 때 재시도가 급증하는 위험을 감수할 만큼의 이득은 아니라고 판단했다.
- 여러 SKU를 한 주문에서 차감할 때는 id 오름차순으로 차감해 데드락을 막는다. 이 잠금 순서는 회원 행을 먼저 잠그는 규칙과 함께 주문 생성·취소·만료 경로 모두에 적용한다.

낙관적 락을 채택하게 되면 운영 마이그레이션에 `sku.version` 컬럼 하나를 추가하면 된다.

## 6. 재현

```
./gradlew :backend:test --tests '*StockLockComparisonTest' -i
```

표준 출력에 `| 방식 | 소요(ms) | 재시도 |` 형식의 줄이 방식마다 하나씩 나온다.
